# Research: Cloud transcription option for Murmur

## TL;DR / Verdict

**Don't build it — not yet, and not as a blanket feature.** Four independent angles (provider landscape, architecture fit, competitive positioning, genuine technical motivation) converge on the same shape of answer from four different directions:

- **The motivation that used to exist (heat/speed) was already fixed** by the live-loop heat-fix shipped in PRs #230–#236 (VAD gate + `flash_attn` + `audio_ctx` sizing + thermal governor + conditional `large-v3-turbo-q8_0` default) — modeled as a 6–50× compute cut, but **never actually measured on real watts** (the `measure-live-power.sh` instrument exists, committed, and has simply never been run).
- **The accuracy upside is thin-to-nonexistent, especially for Polish** — an independent academic benchmark (BIGOS V2, NeurIPS 2024) already found Whisper beating Google/Azure on Polish, and Murmur's own in-house A/B already flipped to `large-v3-turbo-q8_0` at zero extra batch cost, closing most of the local Polish-quality gap for free.
- **The competitive case is actually negative, not neutral** — no meeting-notes incumbent (Granola/Otter/Fireflies/Fathom/tl;dv) offers local transcription at all, so Murmur's differentiation is already fully earned by *having* local; adding cloud doesn't add much more to that story and risks the one documented real-world failure mode in this space (Superwhisper: not backlash for offering cloud, but user confusion about which mode processed which recording).
- **The one motivation that survives scrutiny — Intel Mac / weak-hardware fallback — is real but completely unmeasured.** `whisper-rs` is compiled with Metal unconditionally, Murmur ships a universal binary (Apple Silicon + Intel), but CI runs exclusively on `macos-14` (Apple Silicon) — the Intel path has *zero* automated verification, and nobody has timed a real transcription on a real Intel Mac or run `powermetrics` against the shipped heat-fix.

**If this is ever built, it should be scoped narrowly** (a consented, clearly-labeled fallback for weak hardware — never a general "faster/better" upsell) **and only after a cheap measurement spike proves the problem is real.** The architecture for *how* to build it is fully designed below and ready to pull off the shelf the moment that measurement justifies it.

## Co już mamy (z repo, z file:line)

- **Transcription has no provider trait today** — unlike `SummarizerProvider`. `src-tauri/src/transcribe/whisper.rs` calls `whisper_rs::WhisperContext` directly (`Transcriber::load` `whisper.rs:106`, `transcribe_with` `whisper.rs:159`); call sites are concrete, not trait-dispatched (`pipeline.rs:177`, `audio/listener.rs:94`, `transcribe/live.rs:1801`).
- **But a near-identical seam already exists for exactly this shape of problem**: `LiveAsr` (`src-tauri/src/transcribe/live_asr.rs:35-43`) — a minimal, object-safe, `Send + Sync` trait already swapping between two *local* engines (whisper vs. NVIDIA parakeet-tdt-0.6b-v3 via `sherpa-onnx`), with a pure, unit-tested, fail-open fallback matrix (`should_use_parakeet`, `live_asr.rs:82`). This is the template for a cloud seam, not `SummarizerProvider`.
- **The redaction firewall is text-only by construction, and structurally cannot cover audio.** `RedactingProvider` (`src-tauri/src/summarize/redact.rs:540-917`) scrubs every `String` field of a `SummarizeRequest` via regex + an on-device NER model — there is no mechanism here (or possible one, short of transcribing first) that could touch a raw WAV byte stream. Cloud transcription cannot borrow the "we redact before it leaves" credibility that makes the existing `anthropic` summarizer path defensible.
- **A four-deep precedent for purpose-scoped consent flags already exists** in `src-tauri/src/settings/config.rs`: `cloud_egress_consented` (`:257-268`, redacted-text-to-LLM), `share_egress_consented` (`:269-281`, E2EE full-content note sharing — explicitly *not* redacted, its own flag "because a link share is a deliberate FULL-CONTENT transfer"), `org_egress_consented` (`:282-291`), `web_search_consented` (`:382-390`). Each has its own `consent_to_X`/`revoke_X` command pair, fail-closed default, preserve-only on settings save. Raw-audio egress is architecturally the same class as `share_egress_consented` (full, unredacted content leaving the device) — the codebase's own precedent argues for a fifth, distinct flag, not reuse of `cloud_egress_consented`.
- **The live-loop heat-fix is real and shipped**, not just modeled-on-paper: Silero VAD tick gate, `flash_attn(true)`, `audio_ctx=832` on the live path, a full thermal governor reading real `NSProcessInfo.thermalState` (`src-tauri/src/thermal.rs:147`), and a RAM-conditional default model (`large-v3-turbo-q8_0` vs `small`, `src-tauri/src/transcribe/model.rs:87-126`). N-way diarization on the "others" stream also shipped (pyannote + CAM++ via `sherpa-onnx`, `pipeline.rs:560,592`) — this already supersedes the old "every remote participant collapses into one label" gap that used to be a candidate cloud-diarization argument.
- **Our own measured Polish baseline** (`docs/research/2026-07-09-transcription-performance.md`): `large-v3-turbo-q8_0` costs the *same* batch wall-clock as `small` (~2.7s for a 131s clip) with near-perfect Polish vs. `small`'s garbled names/dropped segments/hallucination loops. This is the real bar any cloud candidate has to clear — not a generic "local Whisper is bad" strawman.
- **Zero cloud-STT code exists anywhere in the tree** (confirmed by grep across `src-tauri/src/` for every major vendor name) — and no dedicated consent/egress gate exists on the audio/transcribe path at all, since today literally no audio bytes ever leave the device.
- **`docs/ARCHITECTURE-LOCAL-CLOUD.md`** (2026-06-26, decision-ready draft) never scoped cloud transcription and explicitly states as an invariant: *"Audio never syncs... The polished note is the only thing designed to leave."* This is a genuinely new egress class, not a gap the prior cloud-architecture work anticipated.

## Findings

*(Four independent murmur-researcher angles; full detail in each agent's brief, condensed and cross-checked here.)*

### 1. Architecture fit — how it would plug in (high confidence, code-grounded)

A `TranscriptionProvider` trait modeled on `LiveAsr` (not `SummarizerProvider`) — one method, object-safe:
```rust
#[async_trait]
pub trait TranscriptionProvider: Send + Sync {
    fn id(&self) -> &str;
    async fn availability(&self) -> Availability;
    async fn transcribe(&self, wav_path: &Path, lang: Option<&str>) -> Result<Transcript>;
}
```
The existing `Transcriber` becomes one (local) implementor, unchanged. A **new, fifth consent tier** (`audio_egress_consented`) is the correct design — not reuse of `cloud_egress_consented` — because reusing it would silently broaden what an *already-granted* consent (for redacted-text-only egress) now also permits, the moment cloud transcription ships; that's the opposite of the CLAUDE.md rule "new cloud egress must be loud and justified." Dual-stream (Me/Others) transcribes as two independent buffers today (`pipeline.rs:150-192,257,301-316`) — a cloud path should keep that shape (two calls, preserve attribution) rather than merging first and losing it. Any "re-transcribe via cloud" command on existing meetings must copy the exact lock-gate `resummarize` already uses (`commands.rs:7902-7906`, `meeting_is_unlocked` before reading audio) — a locked folder's audio must be as unreachable to a new cloud path as to every existing read path. The egress ledger and Privacy Receipt both need small, mechanical extensions (a new `call_kind: "transcribe_audio"`, a new front-matter fact distinguishing transcription-host from summarize-host) — the ledger addition is trivial; the Privacy Receipt schema change needs a short dedicated design pass, not a copy-paste. **Effort: M for batch-only with one provider; L if live/streaming is also pursued** (needs a new WebSocket dependency, subject to the repo's no-new-crates-without-approval rule, and is a genuinely different architecture, not a variant).

### 2. Provider landscape — what's actually out there (high confidence on pricing/language support, medium on accuracy claims)

Cloud STT is a commodity in 2026. If pursued, **Groq-hosted `whisper-large-v3-turbo`** is the standout pick: **$0.04/hour**, the *same model family* Murmur already trusts locally (zero new accuracy story to sell), a plain REST multipart upload (zero new crates — `reqwest` already does this), batch-only. Deepgram Nova-3 is the only candidate with a genuine low-latency streaming WebSocket API and Polish support (monolingual model only, not the multilingual/code-switch variant) — but its Rust SDK is explicitly community-owned/pre-1.0, and it only matters *if* live cloud captions are the actual goal (see Finding 4 below — they're not). AssemblyAI is **disqualified for Polish streaming specifically** (Polish is absent from every AssemblyAI real-time language list, batch-only). OpenAI's `gpt-4o-transcribe-diarize` is the one candidate with native first-party multi-speaker diarization in the same call — interesting only if per-person "others" diarization becomes a priority independent of the cloud question (and Murmur already shipped a local pyannote-based version of this). Google and Azure are the **weakest** picks specifically for Polish — the same independent BIGOS V2 benchmark that validates Murmur's local model choice found Whisper beating both.

### 3. Competitive framing — does this help or hurt positioning (medium-high confidence, well-sourced)

No cloud-native meeting-notes incumbent (Granola, Otter, Fireflies, Fathom, tl;dv) offers local transcription at all — several (Granola specifically) actively co-opt "local"/"device-level" language in marketing for what is, verified, a 100%-cloud pipeline. Murmur's differentiation ("nothing leaves your Mac") is **already fully earned by having local transcription today** — adding an opt-in cloud mode on top doesn't meaningfully deepen that claim, since the claim's power comes from the *default*, not from lacking alternatives. The closest real precedents for "local-by-default, clearly-labeled opt-in cloud" are **Obsidian itself** (the platform Murmur lives inside — local core, separately-branded paid "Obsidian Sync") and **Superwhisper** (whisper.cpp local by default, an explicitly-labeled "Ultra" cloud tier). Superwhisper's one documented failure mode is instructive and specific: not backlash for *having* a cloud option, but its privacy policy **not clearly distinguishing, per-use, which mode handled that specific recording** — a labeling-discipline problem, not a conceptual one. The Rewind→Limitless abandonment of local-first is a real cautionary tale but weaker than it first appears: the concretely-verified driver was **performance/battery complaints** ("turned MacBooks into a toaster" — continuous 24/7 screen recording, a much heavier workload than Murmur's episodic meeting transcription), not a stated user preference for cloud; the "users didn't prioritize local-only" framing is the article author's inference, not a quoted survey.

### 4. Genuine technical motivation — is there a real problem to solve (medium confidence — the honest gap is measurement, not architecture)

The heat/speed motivation that would have justified cloud most directly **was already addressed** by the shipped heat-fix — modeled as a 6–50× live-loop compute reduction — but **that number has never been verified on real watts**; the `measure-live-power.sh` `powermetrics` harness exists, committed, and has simply never been run since the fix shipped. The OOM crash from the 2026-07-07 perf audit was primarily an LLM/brain-residency problem (`combined_residency_gb` doesn't even include whisper's RAM), not a transcription one, and is largely moot now that the default model dropped from `large-v3` (~3.1GB) to `small`/`turbo-q8_0` (~470MB–1.2GB). **Live/streaming captions would NOT benefit from cloud** — the bottleneck is Murmur's fixed 3-second-tick/14-second-window re-decode architecture (`live.rs:35`, `WINDOW_SECS`), not local engine throughput; a cloud call adds real network round-trip latency (200–500ms+) *on top of* that fixed cadence rather than removing it, unless the live loop is separately rewritten to be genuinely streaming (an engine-agnostic fix already scoped as future work, "T4," that would help local and cloud identically). **The one motivation that survives**: Murmur ships a universal binary (`aarch64` + `x86_64-apple-darwin`) with `whisper-rs` compiled `features=["metal"]` unconditionally, but CI runs exclusively on Apple-Silicon `macos-14` — the Intel/CPU-only fallback path has shipped to real users with **zero automated verification, ever**. External benchmarks suggest CPU-only whisper.cpp (no Metal) runs meaningfully slower (~4×, medium-confidence blog source), and one old, unconfirmed GitHub issue reports Intel+Metal producing garbled (not just slow) output. This is a real, falsifiable, currently-unmeasured gap — not a guess dressed up as a finding.

## Fit z ograniczeniami Murmur

- **Local-first / privacy (non-negotiable #1)** — the load-bearing tension across all four angles. Raw audio leaving the device is categorically more invasive than today's only cloud path (redacted *text* to `anthropic`) — there is no equivalent of the redaction firewall for audio, so any cloud-STT feature has to earn its "loud and justified" bar on its own, without borrowing the summarizer path's existing credibility. All four agents agree this bar is not currently cleared for a blanket feature.
- **Provider seam stays intact** — a **new**, parallel `TranscriptionProvider` seam, not a stretch of `SummarizerProvider` over data it was never designed for. Confirmed clean by the architecture-fit agent.
- **SQLite-canonical / Obsidian-native** — unaffected either way; a cloud-produced `Transcript`/`Segment` set lands in the same schema local whisper produces today.
- **macOS-first / CI honesty** — batch/REST cloud STT is, unusually for this codebase, one of the *lower*-risk pieces to build and verify (a plain HTTP call, headlessly testable with a mock server) — no ScreenCaptureKit/TCC/Touch-ID entanglement. The Intel-fallback motivation is itself a CI-honesty gap: Apple-Silicon-only CI means Murmur cannot currently prove what it ships to Intel users actually works well.
- **No new dependencies** — batch/REST (the only variant worth pursuing, per Finding 4) needs **zero new crates** (reuse `reqwest`, mirror the existing `gateway.rs` OpenAI-compatible client pattern). Streaming/live cloud would need a new WebSocket crate, subject to explicit user approval — one more reason live/streaming is the wrong scope to reach for.

## Opcje i tradeoffy

1. **Do nothing (status quo).** Effort: none. Risk: none. Preserves the cleanest, most defensible version of "nothing leaves your Mac" — the claim every prior competitive research report on this product has independently converged on as the strongest, most structurally uncopyable wedge against the entire cloud-native competitor set. Cost: the Intel/weak-hardware gap stays open and unmeasured.

2. **Measure first (no product code).** Effort: S. Run the already-committed `scripts/measure-live-power.sh` for real watts on the shipped heat-fix (converts "modeled 6–50× cut" into a fact), and time a real (or CI-added `x86_64`/CPU-only) whisper batch transcription to see if Intel/low-RAM is actually painful. Risk: none — pure measurement, matches the project's own "measure before you build" discipline already used for the Brain v2 eval gate. **This is the recommended next step.**

3. **Narrow, consented cloud fallback for weak hardware only** (batch, Groq-hosted `whisper-large-v3-turbo`, new `TranscriptionProvider` + `audio_egress_consented` gate, Superwhisper-style permanent per-recording label of which pipeline processed that specific meeting). Effort: M. Risk: low-medium *if and only if* option 2 justifies it first — same model family as local (no new accuracy story), cheapest vendor, zero new deps, smallest privacy-surface increase of any cloud-STT shape considered. This is the one form of "cloud transcription" that survived scrutiny across all four angles, and only conditionally.

4. **General "cloud tier" as a speed/quality upsell for all users.** Effort: L. Risk: high — this is the shape most likely to read as "abandoning the privacy promise" (per the competitive-framing angle), is not supported by any measured accuracy gap (per the provider-landscape and motivation angles — Polish accuracy is already close to parity or better locally), and would need a new streaming dependency if the goal is live captions, which the motivation angle shows wouldn't even solve the latency problem. **Not recommended at any point without new evidence.**

5. **Live/streaming cloud captions specifically.** Effort: L. Risk: high, and — uniquely among these options — **the evidence says it wouldn't work anyway**: the live-loop's latency ceiling is architectural (fixed-window re-decode cadence), not engine-speed-bound, so cloud network round-trip would likely make perceived caption latency *worse*, not better, absent a separate, local, engine-agnostic streaming-loop rewrite that's already on Murmur's own roadmap (Brain v2 "T4") and would help local and cloud identically. **Do not pursue this to solve a live-caption problem; if T4 ships, re-evaluate then.**

## Rekomendacja i pierwszy krok

**Recommend Option 2 (measure first), full stop — this closes the actual open question before any product decision is made.**

Two concrete, cheap, code-free-or-nearly-so actions, in order:

1. **Run `scripts/measure-live-power.sh` with `sudo powermetrics` on a real Mac**, capturing the live-loop's actual watts/thermal transitions under the shipped heat-fix. This turns "we believe we fixed the heat problem" into a verified fact or a real remaining gap — either answer is useful and it costs nothing beyond running an already-written script.
2. **Time a real (or CPU-forced) whisper batch transcription** — ideally on an actual Intel Mac, or failing that, a CPU-only-forced run on any Mac, or a one-off `x86_64` timing job added to CI (not full CI, just a timing probe) — against a realistic ~10-minute meeting WAV. If CPU-only transcription comes in meaningfully slower than real-time, that is the evidence-backed trigger for Option 3; if it doesn't, the Intel-fallback motivation closes too, and cloud transcription has no surviving justification at all.

**Only if step 2 finds a real problem**, the next step is the spike the architecture-fit and provider-landscape agents both independently converged on: wire a minimal `TranscriptionProvider` implementation against Groq's OpenAI-compatible `/v1/audio/transcriptions` endpoint, gated by a new `audio_egress_consented` flag (never reusing `cloud_egress_consented`), tested headlessly with `cargo test --lib` against a fake in-process provider (no real vendor call needed to prove the trait/consent-gate wiring is correct) before spending any effort on the real HTTP integration.

## Otwarte pytania / czego nie udało się zweryfikować

- **No real-Mac watts/thermal measurement exists anywhere in this repo** for the shipped heat-fix — the single biggest gap, and the literal first step above.
- **No real Intel Mac or base-RAM M1 timing measurement exists** for whisper transcription — asserted as plausible from general external whisper.cpp benchmarks, not measured on Murmur's own build.
- Whether whisper.cpp 1.8.3 (vendored version) still has the Intel+Metal garbled-output issue reported in a Nov 2023 GitHub issue is unconfirmed — could be long-fixed.
- No independent, non-vendor WER benchmark head-to-head across all six surveyed cloud vendors on Polish specifically exists; BIGOS V2 is the strongest signal found but pre-dates each vendor's most recent 2026 model refresh.
- Data-retention/training policies for every cloud vendor were confirmed only at medium confidence from docs/support pages, not primary ToS/DPA documents — would need a direct legal read before any consent copy is written.
- The exact Privacy Receipt front-matter schema extension (to represent "this note's audio, not just its summary, touched the cloud") was identified as a gap but not designed — needs its own short spec pass if Option 3 is ever built.
- Whether the redaction firewall could plausibly be extended to audio (e.g., local diarize + redact before any hypothetical upload) was not investigated — would materially change the privacy-fit calculus if revisited.
