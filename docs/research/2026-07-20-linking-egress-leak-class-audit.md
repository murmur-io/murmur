# Audit: leak / collision / content-loss classes around linking + sharing

**Trigger.** The user found two real bugs — (1) the machine `murmur:links` "Related notes" block leaking linked-note **titles** through note share, and (2) the backlink content-scan matching by **title string** (default "Untitled" fans out). They asked to sweep for more of the same **classes**. This is the grounded result: 5 parallel read-only finders (managed-content egress, title-string collision, content-loss/clobber, egress-firewall, visibility-gate) → an adversarial refute pass on every HIGH/MEDIUM finding. **0 refuted.**

## TL;DR / Verdict

- **The share leak is broader than `murmur:links`.** There are **three** machine-managed fences — `murmur:links`, **`murmur:context`** (`> [!context]- Live context`), **`murmur:verify`** (`> [!verify]- Source check`) — and **no share/org egress scrub strips any of them**. `murmur:context`/`murmur:verify` carry **live connector content** (Jira issue keys/statuses, Slack channel snippets, and workspace-identifying `https://…atlassian.net` / Slack permalink URLs), so sharing an enriched/verified note leaks the sender's private third-party data — **strictly worse than the title leak**. **HIGH.**
- **Reachable content-loss (clobber) is confirmed**: a backend note-body write (accept-link / +Link / Enrich / Verify) is silently overwritten by the note-editor's **stale-body debounced autosave**, destroying the just-written block (and any pending prose) in the DB *and* the vault `.md`, no error. **MEDIUM.**
- Several **title-string-not-ID** collisions beyond bug #2 (Related-chip suppression, Vault-Audit orphan/unlinked passes) — real but **LOW** (display/data-quality only, mostly self-healing).
- **No sealed-content / visibility-gate leak found** (the gate discipline holds across detail/MCP/graph/backlinks/share — both endpoints gated). The egress leak is *managed-block-not-stripped*, not *sealed-content-served*.

## Confirmed findings (ranked)

### 1. [HIGH] Connector-data egress leak — `murmur:context` + `murmur:verify` blocks unstripped on share
- **Persistence:** `commands/enrich.rs::apply_note_enrichment_inner` → `enrich::apply_context_markers` and `apply_note_verify_markers_inner` → `verify::apply_verify_callout` write these fenced blocks into the **canonical** `note.markdown` (+ re-export the vault `.md`). Each line carries real connector data, e.g. `> - PROJ-123 · In Progress · due 2026-08-01 (via Jira) — https://acme.atlassian.net/browse/PROJ-123` and Slack `#eng` snippets + permalinks.
- **Egress gap:** every share path reads the raw `note.markdown` and scrubs with only `share/envelope.rs::clean_note_body` (= `strip_frontmatter` + `flatten_wikilinks`) and, for org, `commands/org.rs::scrub_org_markdown` (= `redact` EMAIL/CARD/PHONE only). A repo-wide grep of `src/share/` + `commands/org.rs` for `murmur:context`/`[!context]`/`[!verify]`/`apply_context_markers` = **empty**. `flatten_wikilinks` strips `obsidian://` but **not** `https://`, so the workspace host + issue keys egress verbatim. Reached by link-share (`share_note_to_link_inner`) and org-share (`build_org_share_body`), both with no preview on the link path.
- **Scenario:** user with a Jira/Slack connector runs Enrich or Verify on a note, then shares it by link or to an Org → recipient gets the sender's ticket keys/statuses, Slack snippets, and the identifying workspace URL.
- **Fix (being applied now, in the murmur:links change):** generalize `clean_note_body` to strip **all three** managed fences, each **header-gated** (only strip a fence whose first body line is its exact `[!related]`/`[!context]`/`[!verify]` callout header, so user prose with a forged bare fence is never eaten). Egress-only — the blocks stay visible in-app (they're features); they just never reach the wire.

### 2. [MEDIUM] Content-loss: backend note-body write clobbered by the editor's stale-body autosave
- **Mechanism:** `accept_link`/`link_items`/Enrich/Verify rewrite the DB `note.markdown` out-of-band. The open `NoteEditorComponent` isn't notified (`app-connections` emits no `output()`; no Tauri event; `onLockTreeChanged` early-returns), so `body()` stays stale. The next keystroke (`scheduleSave`) or a tab-switch (`flushFull`, `dirtyFull` already set) serializes the stale block-less body and `update_note_row` **full-body overwrites** the DB row + re-exports the vault `.md` — silently destroying the just-written block.
- **Note:** the murmur:links elimination (this session's main change) removes the accept/+Link materialization → *that* clobber source is gone. But **Enrich/Verify still write the body**, so the pattern survives for them. Proper fix (follow-up): the FE editor must **reload or merge** after any backend body mutation (a `(changed)` output → `hydrate()`), never blind-overwrite from a stale body.

### 3. [LOW] `connections.relatedRows` suppresses a Related chip by title string
- `edge.edgeType==="wikilink" && !edge.manual && inline.has(edge.otherTitle.toLowerCase())` — a title-string match with no id/direction. A renamed or duplicate-titled neighbour can be suppressed even though the body's `[[Title]]` resolved to a *different* id. Mostly self-heals via the inbound-backlink safety-net (survives as a "mentions" row); the hard-loss case needs a rename. **Display-only.** Fix: key the suppression on resolved `otherId`, not the title string.

### 4. [LOW] Vault Audit `orphan_pass` / `unlinked_mention_pass` key on title
- `by_title: HashMap<&str, Vec<usize>>` sets `has_in[j]` for **every** same-titled doc; `unlinked_mention_pass` records a `target_id` the accept path may re-resolve to a *different* same-titled note. False-negatives / mis-attribution in a data-quality tool for duplicate titles ("Untitled"). Fix: resolve to id.

### 5. [LOW · PLAUSIBLE] `strip_fenced_block` eats user prose on a colliding fence
- The read/strip path applies no `sanitize` to the *base* note, so a note whose own prose contains the literal `<!-- murmur:links -->`…`<!-- /murmur:links -->` markers loses the content between them. **This is being closed in the current change** by header-gating every strip (only strip a real block with its callout header).

### Bug #2 (the user's, for the record): backlink content-scan matches by title
- `storage/links.rs::backlinks_for_visible` "Gate 2" content-scan does `extract_wikilink_titles(body).contains(target_title)` → default-"Untitled" fan-out. **Queued as its own PR** (resolve `[[Title]]` → id like `resolve_wikilink`/`index_wikilinks_for_source`; never match empty/default titles).
