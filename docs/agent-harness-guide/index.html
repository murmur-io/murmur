Murmur development harness · przewodnik od zera

Nie „AI robi kod”.
System pilnuje pracy AI.

Gdy zlecasz agentowi zmianę w Murmurze, harness daje mu osobny katalog pracy, wyznacza granice, uruchamia testy i niezależne review — a potem pozwala zacommitować wyłącznie dokładnie sprawdzony kod.

07 · role i formularze

Prompty mówią jak działać. Schemas mówią jak zwrócić wynik.

PROMPTS/

Instrukcje ról

  • implementer.md — writer: scope, bez commita, bez PASS
  • spec-reviewer.md — czy zrobiono to, o co proszono?
  • adversarial-reviewer.md — spróbuj złamać zmianę
  • lock / egress / protocol — dodatkowe ryzyka
SCHEMAS/

Formularze dla programu

  • task.schema.json — kontrakt ma komplet pól
  • review.schema.json — verdict i findings
  • attestation.schema.json — exact diff + dowody
  • commit.schema.json — prawdziwy commit receipt

Prompt mówi agentowi, jak ma działać. Schema wymusza, jak ma zwrócić wynik.

11 · gdy coś failuje

FAIL mówi, którą warstwę workflow wzmocnić.

REAL TASK FAIL

Zmiana nie przechodzi.

  1. Runner daje writerowi log testu albo finding reviewera.
  2. Writer ma maksymalnie dwie rundy napraw.
  3. Jeśli nadal failuje: FAILED albo BLOCKED.
  4. Nie ma attestation, commit ani PR z tego taska.
EVAL FAIL

Agent zawiódł na egzaminie.

  1. Operator czyta trace i ustala, czego agent nie umie.
  2. Poprawia regułę, prompt, hard guard albo wybór roli.
  3. Powtarza eval kilka razy.
  4. Nie zmienia się nic automatycznie w Murmurze.

status i verify-attestation tylko czytają. Push i PR są świadomą, zewnętrzną decyzją operatora.
