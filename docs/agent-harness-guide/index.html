Murmur development harness · przewodnik od zera

Developer robi zmianę.
Harness weryfikuje dowód.

Harness nie uruchamia implementera i nie naprawia kodu. Tworzy izolowany worktree, wyznacza granice, dobiera checki z dokładnego diffu i oddaje verdict świeżemu reviewerowi.

07 · review i formularze

Jeden review łączy zgodność ze specem i próbę złamania zmiany.

PROMPTS/

Instrukcje review

  • combined-reviewer.md — spec + adversarial w jednym verdictcie
  • lock-security-reviewer.md — tylko gdy diff dotyka locka
  • egress-security-reviewer.md — tylko dla egressu
  • protocol-security-reviewer.md — tylko dla protokołu
SCHEMAS/

Aktualne dokumenty

  • v2-task.schema.json — kontrakt
  • v2-plan.schema.json — profil exact diffu
  • v2-review.schema.json — verdict, findings i proof gaps
  • v2-evidence / v2-commit — dowód i receipt

Reviewer jest świeży, read-only i bez narzędzi. Komendy wykonuje wyłącznie runner.

09 · resume

Przerwanie nie zeruje dobrego dowodu.

CHECKPOINT

zielony check

Wynik jest związany z diffem, planem i protokołem.

→
PRZERWANIE

timeout / 429 / crash

Stan przechodzi w typowany retry zamiast terminalnego BLOCKED.

→
KONTYNUACJA

resume

Runner wykonuje tylko brakujący albo retryable fragment.

Gdy diff się zmieni, powstaje świeży attempt. Gdy diff jest identyczny, zielony dowód pozostaje ważny.

11 · gdy coś failuje

Stan mówi dokładnie, co zrobić dalej.

NEEDS_FIX

Kod albo kontrakt nie spełnia wymagań.

  1. Czytasz finding i runner-owned log.
  2. Naprawiasz ten sam worktree.
  3. Uruchamiasz verify.
  4. Nowy diff dostaje nowy attempt.
NEEDS_EVIDENCE / RETRY

Kod nie musi się zmieniać.

  1. Brakuje proofu albo zewnętrzny proces przerwał pracę.
  2. Uruchamiasz resume.
  3. Zielone checkpointy są ponownie użyte.
  4. Nie przenosisz patcha ręcznie.
